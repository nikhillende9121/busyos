# 0003: Two-Layer Authorization — Feature Flags Before RBAC

## Status

Accepted (already encoded in `AI_AGENT.md`; recorded here as the formal
decision record).

## Context

A single permission system (e.g. "does this user have `PRODUCT.CREATE`?")
conflates two different questions: what the *tenant* has paid for, and what
a *specific user within that tenant* is allowed to do. Checking permissions
alone would let a tenant whose plan no longer includes, say, the Purchase
module keep using it as long as an employee's role still carries
`PURCHASE.CREATE` — because downgrading a plan doesn't retroactively strip
permission bits from every role.

## Decision

Two independent, ordered checks on every request:

1. **Feature Validation** — is this module enabled for the tenant's current
   plan/subscription (`tenant_features`, `plan_features`)?
2. **Permission Validation (RBAC)** — does the authenticated user's role
   grant this specific action (`role_permissions` → `permissions`)?

Feature validation always runs first; a disabled feature must reject the
request before RBAC is even evaluated.

## Consequences

- Downgrading a tenant's plan immediately locks out a module for every user
  in that tenant, without touching any role's permission set.
- The two checks can be tested and reasoned about independently — a bug in
  role assignment can't accidentally grant access to an unpurchased module.
- Every new module must register both a feature flag (if it's meant to be
  plan-gated) and its permission set (`<MODULE>.VIEW/CREATE/UPDATE/DELETE`)
  — see `MODULE_GUIDE.md` checklist. Forgetting either means the module is
  either always-on (no feature check) or unreachable (no permissions
  granted to any role).
